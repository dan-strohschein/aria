## Discovered during v0.2 implementation

### 1. Variant name collisions across sum types and built-ins

User-defined sum-type variants can silently collide with built-in variants (e.g. `Option::None`). A user writing their own `type Outer = | Wrap(Inner) | None` will find `val := None` constructs `Option::None` not `Outer::None`. Currently worked around by renaming in tests (`nested_pattern_test.aria` uses `Nothing`).

**Fix direction**: Qualified construction (`Outer::None`) or contextual resolution based on expected type in expression position.

### 2. Closure type-tracking beyond str/i64

The v0.2 follow-up for `fn(str) -> str` closures landed as a narrow special-case: `_lower_closure` string-matches the literal `"str"` in param/return annotations to decide slot allocation and return convention. More complex closure signatures still lose type information:

- `fn(MyStruct) -> MyStruct` (struct params/returns)
- `fn([i64]) -> [i64]` (array params/returns)
- `fn(fn(i64) -> i64) -> i64` (higher-order — closures taking closures)
- `fn(i64) -> (i64, str)` (tuple returns)

**Fix direction**: Replace the string-matching with a proper closure-type parser that resolves each annotation to a TypeInfo and uses it to size IR params and set return type.

### 3. Verify `@once_unchecked` escape hatch actually landed

The Sprint 3 plan specified `@once_unchecked` as an annotation to bypass once-closure consumption tracking. It's not clear whether the parser/checker wiring shipped end-to-end or only the core enforcement did.

**Action**: Audit Sprint 3 commits; add minimal test; wire parser + checker if missing.
